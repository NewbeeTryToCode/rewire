## 1. What is each project (type, language, license, size, activity, tests, benchmarks)?

### Takeaway
cortex-works/cortex-db is a placeholder repo: a README, an MIT license, a release script and no source code. Everything it describes (SQLite plus LanceDB for Scrum tickets and agent memory) is a plan. CortexaDB is a real project: an embedded, single-process Rust library with PyO3 Python bindings, MIT OR Apache-2.0 licensed, about 14k lines in total. It has 229 Rust tests, which pass, a 36-test Python suite and CI. It is labelled "v1.0.1 stable", but it is a one-author project, about 59 stars, and its only benchmarks measure ANN speed and recall, not memory quality.

## 2. Graph model (schema, edge types, traversal, edge creation, temporal handling)

### Takeaway
CortexaDB has a minimal directed, labelled adjacency list held in memory. Edges are `{to, relation: String}` with no weight, timestamp, confidence or provenance. They are created only by an explicit `connect()` call (no LLM, rule or embedding-based linking) and must stay within one collection. Traversal is plain BFS/DFS/shortest path. Retrieval uses it only to widen the candidate set, after which every candidate is re-scored by its own cosine similarity. There are no temporal edges, no spreading activation and no relation-type semantics. cortex-db has no graph.

### Cited Findings
- Node = `MemoryEntry { id: MemoryId(u64), collection: String, content: Vec<u8>, embedding: Option<Vec<f32>>, metadata: HashMap<String,String>, created_at: u64, importance: f32 }` — [core/memory_entry.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/core/memory_entry.rs)
- Mutations are a 4-variant command log: `Add(MemoryEntry)`, `Delete(MemoryId)`, `Connect{from,to,relation}`, `Disconnect{from,to}` — [core/command.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/core/command.rs)
- State: `memories: HashMap<MemoryId, MemoryEntry>`, `graph: HashMap<MemoryId, Vec<Edge>>` and `temporal_index: BTreeMap<u64, Vec<MemoryId>>`. `connect` deduplicates on (to, relation) and keeps edges sorted. `disconnect(from,to)` removes **all** relations between the pair. Delete removes incoming edges by scanning every adjacency list — [core/state_machine.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/core/state_machine.rs) (L27-150)
- Cross-collection edges are rejected (`test_cross_collection_edge_rejected`) — [core/state_machine.rs L405](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/core/state_machine.rs)
- Traversal: `GraphIndex::bfs` returns id → hop distance, outgoing edges only. There are also `dfs` (all paths up to a depth) and `find_path` (BFS shortest path). Relation labels are ignored during traversal (`for (neighbor_id, _relation) in neighbors`) — [index/graph.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/index/graph.rs)
- Edge creation is manual only, through `db.connect(mid1, mid2, "relates_to")` in Python or `connect` in Rust. A grep across core and Python found no automatic linking, entity extraction or LLM calls — [README.md quickstart](https://github.com/anaslimem/CortexaDB/blob/main/README.md), [client.py `connect`](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-py/cortexadb/client.py)
- "Temporal" means only `created_at` (seconds since epoch, set at insert) with a BTreeMap range query (`TemporalIndex::get_range`). There is no valid-from/valid-to, no supersession and no event time distinct from ingest time — [index/temporal.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/index/temporal.rs), [facade.rs `add_in_collection`](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/facade.rs)
- The README calls the project "graph relationships, and temporal indexing", which is accurate only in this minimal sense — [README.md](https://github.com/anaslimem/CortexaDB/blob/main/README.md)

### Inferences
- As a graph model it is weaker than what rewire can already express with markdown nodes and links. It has no edge provenance or time, so it cannot represent "A replaced B at time t" or belief revision.
- The most reusable idea is the retrieval pattern "graph widens the candidate pool, then everything is re-scored by its own similarity" (section 4). It is conservative: a neighbour that is not semantically relevant cannot win just by being linked.

### Gaps
- None for the code. Whether the author plans richer edges is unknown; there is no roadmap file.

## 3. Storage and indexing (file formats, vector index, persistence, embeddings, dependencies)

### Takeaway
A database is a directory holding a CRC32-framed bincode WAL of commands (`cortexadb.wal`), CRC32-framed bincode segment files of entries (`segments/NNNNNN.seg`), a checkpoint snapshot and an optional usearch HNSW file. The whole state lives in RAM as HashMaps and is rebuilt on open from checkpoint plus WAL. The vector index is exact brute-force cosine by default (rayon-parallel) or HNSW via usearch (M=16, efC=200, efS=50). Embeddings come from the caller or from Python providers (OpenAI, Gemini, Ollama). The binary formats are not human-readable and not git-diffable.

### Cited Findings
- WAL record: `[u32 command_len][u32 crc32][bincode(Command)]`. A tolerant reader truncates a corrupt or partial tail to `valid_bytes`. `truncate_prefix` drops entries already covered by a checkpoint — [storage/wal.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/storage/wal.rs) (L49-60, L156-240)
- Segment record: `[u32 entry_len][u32 checksum][bincode(MemoryEntry)]`, files named `{:06}.seg`, with rotation and tail truncation — [storage/segment.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/storage/segment.rs)
- Layout on open: `<path>/cortexadb.wal` and `<path>/segments/`. The next id is `max(existing id) + 1` (sequential u64) — [facade.rs `open_with_config`](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/facade.rs) (L226-280)
- The engine writes the WAL first, then the segment, then applies the command to the in-memory state machine. Sync policies are `Strict`, `Batch{max_ops,max_delay_ms}` and `Async{interval_ms}`. There is a background checkpoint thread and segment compaction — [engine.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/engine.rs) (L44-90), [store.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/store.rs), [storage/checkpoint.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/storage/checkpoint.rs), [storage/compaction.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/storage/compaction.rs)
- Concurrent reads use an `arc-swap` published `ReadSnapshot` — [store.rs L56-75, L351](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/store.rs)
- Vector backends: `Exact` (default) and `Ann{ann_search_multiplier}`. Without HNSW, `Ann` mode uses a `PrefixAnnCandidateProvider` that scores **only the first 8 dimensions** of each vector, then reranks exactly. When HNSW is enabled, usearch is used with `MetricKind::Cos`, F32 and `{m:16, ef_construction:200, ef_search:50}`, and falls back to exact search on error — [index/vector.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/index/vector.rs) (L30-80, L414-470), [index/hnsw.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/index/hnsw.rs)
- The HNSW path calls `hnsw.search(query, top_k, None)` and **ignores the collection**, so collection scoping relies on post-filtering. `search_in_collection` over-fetches 4× top_k globally and then filters — [index/vector.rs L440-447](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/index/vector.rs), [facade.rs L387-421](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/facade.rs)
- The Python default is `index_mode="exact"`. The project's own guidance: use Exact under 10,000 entries, HNSW above — [client.py L150](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-py/cortexadb/client.py), [benchmarks.mdx](https://github.com/anaslimem/CortexaDB/blob/main/docs/content/docs/resources/benchmarks.mdx)
- Capacity eviction (`max_entries`/`max_bytes`) deletes the oldest first, then the least important — [engine.rs L339-395](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/engine.rs)
- Portability: a separate NDJSON "replay log" (header line plus one op per line, `add`/`connect`/`delete`/...) can be recorded alongside writes or exported, and replayed into a new database with id remapping — [cortexadb/replay.py](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-py/cortexadb/replay.py), [client.py `replay`/`export_replay`](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-py/cortexadb/client.py)
- Chunkers (Fixed, Recursive, "Semantic", Markdown, Json) exist in Rust. "Semantic" is paragraph splitting on `\n\n`, not embedding-based — [chunker.rs L18-42, L224-240](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/chunker.rs)

### Inferences
- There is no keyword index of any kind, so CortexaDB cannot replace rewire's FTS5. Using it as rewire's derived vector index would swap a SQLite table plus brute force (fine at 256-d and rewire's scale, by CortexaDB's own <10k guidance) for a second opaque store with a different consistency model. That is a poor trade.
- The 8-dim prefix "ANN" heuristic is effectively random candidate selection for typical embeddings, which are not ordered by variance. It should not be copied.

### Gaps
- I did not benchmark load and recovery time on a realistic memory size, or memory use for N entries. Everything is held in RAM, so cost grows linearly, but I did not measure it.

## 4. Retrieval (how vector, keyword and graph signals combine; ranking formulas)

### Takeaway
Retrieval is vector-first: cosine top-(k × multiplier), metadata/time filters, optional BFS expansion of 1–3 hops, then re-scoring of the expanded set by cosine. A weighted score `0.7·sim + 0.2·importance + 0.1·recency` (similarity mapped to [0,1], recency min-max normalised *within the candidate set*) is applied **only** when both a time range and graph expansion are set. Otherwise the score is similarity alone. There is no keyword signal. An "intent anchor" mechanism adjusts the weights and hop count from the cosine between the query and three anchor phrases. Through the public facade and Python API this mechanism looks broken (see the findings below), and the Python layer adds its own unrelated graph bonus and 30-day half-life recency bonus.

### Cited Findings
- `ScoreWeights::default() = (70, 20, 10)` (similarity/importance/recency %). `similarity_score = ((cos+1)/2).clamp(0,1)`. `recency_score = (created_at - ts_min)/(ts_max - ts_min)` over candidates. `final = w_s·sim + w_i·imp + w_r·rec` — [query/hybrid.rs L55-90, L262-290](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/query/hybrid.rs), [query/executor.rs `build_ranked_hits` L305-360](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/query/executor.rs)
- The planner picks one of `VectorOnly | VectorTemporal | VectorGraph | WeightedHybrid` and sets a candidate multiplier of 3 (+1 temporal, +2 graph, +1 if top_k>50) and an ANN multiplier of max(2×m, 7). The weighted formula is used only for `WeightedHybrid` (time_range **and** graph); other paths use similarity only — [query/planner.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/query/planner.rs), [query/executor.rs L298-305, L344-348](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/query/executor.rs)
- `QueryOptions::default()` sets `graph_expansion: Some(1)` ("Hybrid-first default: expand one hop"). Graph expansion collects every BFS-reachable id (start included) and re-scores the set with `search_in_ids` by cosine. Graph distance and relation type never enter the score — [query/hybrid.rs L118-133](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/query/hybrid.rs), [query/executor.rs L205-245](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/query/executor.rs)
- Intent anchors: the default policy embeds three phrases ("semantic meaning, similar content, concept match", "recent events, latest updates, time, timeline, schedule", "relationships, connections, linked people, social graph"). Each is turned into `(cos+1)/2`. Similarity/recency weights split the budget left after a fixed importance of 20% in proportion to the semantic and recency scores. Hops become 2 if the graph score ≥0.55 and 3 if ≥0.80. Weights are overridden only while they are still the default 70/20/10 — [query/intent.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/query/intent.rs), [query/planner.rs `infer_intent_adjustments`](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/query/planner.rs), [query/executor.rs L130-158](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/query/executor.rs)
- The executor builds the anchors by calling `embedder.embed(anchor_text)` and caches them **keyed only by dimension** — [query/executor.rs L53-91](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/query/executor.rs). The facade's `search` and `search_in_collection`, which the Python bindings call, pass a `StaticEmbedder` that returns the query vector for *any* text — [facade.rs L150-160, L362-421](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/facade.rs)
- The facade's `search` uses `QueryOptions::with_top_k`, so it inherits 1-hop graph expansion by default even when Python's `use_graph=False` — [facade.rs L362-380](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/facade.rs)
- Python `search()` post-processing: with `use_graph=True`, each base hit's neighbours get `max(existing, parent_score·0.9)`, a score inherited without re-scoring. With `recency_bias=True`, `score *= 1 + 0.2·0.5^(age/30 days)` — [client.py L262-300](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-py/cortexadb/client.py)
- `importance` is never set by the facade or the Python `add` API (`MemoryEntry::new` defaults to 0.0, and the facade add functions never call `with_importance`). The bindings only read it back — [facade.rs L282-330](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/facade.rs), [core/memory_entry.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/core/memory_entry.rs), [cortexadb-py/src/lib.rs](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-py/src/lib.rs)
- No BM25, FTS or keyword matching exists anywhere in core or Python (grep for bm25/keyword/fts/tokeni found none) — local grep

### Inferences
(These are from reading the code; I did not run them.)
- Through the facade and Python, the intent "anchors" all equal the **first query vector ever seen** for that dimension, cached for the life of the process. The hop count (1–3) for every later query then depends on how similar it is to that first query, and the semantic and recency anchors are identical. Given the ≥0.55 threshold on `(cos+1)/2`, any query with cos ≥ 0.1 to the first query gets at least 2 hops. The weight changes have no effect on the facade path anyway, because without a time range the path is `VectorGraph`, which ranks by similarity only.
- So the Python "hybrid" retrieval is in practice cosine top-k over a graph-widened pool, plus optional Python-side multiplicative bonuses. The "Hybrid Retrieval… Vector, Graph and time-based recency in a single query" claim in the README holds only for direct Rust `QueryOptions` users who set both a time range and graph expansion.
- Min-max recency over the candidate set is relative: the same memory's recency score changes with whatever else was retrieved. rewire should prefer absolute age decay, such as the half-life form CortexaDB's Python layer uses.

### Gaps
- I did not confirm the anchor-cache behaviour empirically. A clean demonstration needs a dataset large enough that the vector candidate pool does not already cover every node, and I did not build one.

## 5. Memory-specific features (decay, consolidation, temporal edges, beliefs) and what rewire should copy or skip

### Takeaway
CortexaDB has no consolidation, summarisation, beliefs, contradiction handling, supersession, temporal validity, access-based reinforcement or forgetting curve. The nearest things are a static `importance` field (not settable through the public API), capacity eviction that removes the oldest first, and a Python-only recency bonus with a 30-day half-life. cortex-db has no features at all. The ideas worth borrowing for rewire are small and mechanical: candidate widening along edges with self re-scoring, a per-hit score breakdown, CRC or length framing for append-only logs with tolerant tail repair, and perhaps query-intent routing via anchor embeddings if it is calibrated and evaluated. CortexaDB's storage engine, its HNSW, its prefix-ANN and its relative recency normalisation should not be adopted.

### Cited Findings
- A grep for decay/forget/consolidat/summar/belief/supersed/valid_/expire/ttl across Rust and Python finds only the Python recency bonus (`decay = 0.5 ** (age / (30 * 86400))`) — local grep; [client.py L290-295](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-py/cortexadb/client.py)
- Eviction order: `created_at` ascending, then `importance` ascending, then id — [engine.rs L360-375](https://github.com/anaslimem/CortexaDB/blob/main/crates/cortexadb-core/src/engine.rs)

### Inferences
**Worth copying into rewire (Python and Rust both):**
1. **Graph widening with self re-scoring.** Expand the vector/FTS candidate set by 1 hop over rewire's markdown links or typed edges, then score the new candidates by their *own* similarity or BM25, not an inherited score. This lets multi-hop facts surface without promoting irrelevant neighbours. It is cheap in SQLite (an edges table plus one join). rewire's eval harness should A/B it, because CortexaDB never measured it.
2. **Per-hit score breakdown and stage trace.** Return sim/fts/graph/recency components and per-stage candidate counts. This helps rewire debug retrieval A/Bs and costs almost nothing.
3. **Tolerant tail repair for JSONL events.** On read, ignore or truncate a partial last line after a crash, and optionally store a per-line checksum. rewire's JSONL in git is the source of truth, so a corrupted tail should not break index rebuilds. A JSON field suffices; binary framing is unnecessary.
4. **Absolute half-life recency as a bounded multiplicative bonus** (`score·(1+α·0.5^(age/H))`), as in CortexaDB's Python layer. It is preferable to the min-max-in-candidate-set form, though α and H need tuning on rewire's benchmarks.
5. *(Speculative)* **Intent anchors.** Comparing the query embedding with a few fixed "temporal / relational / factual" anchor embeddings to route weights or hop depth is cheap with a 256-d local embedder. The anchors must be embedded with the real text embedder and cached per model, not per dimension, which is CortexaDB's bug. It should also be checked against rewire's existing query-expansion and category results; there is no evidence it helps.

**Not worth copying:**
- The storage engine (bincode WAL, segments, in-RAM HashMaps): opaque and not diffable, which contradicts rewire's git-native, human-readable source of truth, and it duplicates what SQLite already does well.
- usearch HNSW: needless at rewire's scale (CortexaDB's own docs recommend exact search below 10k), it adds a C++ dependency, it is approximate (95% recall), and here it ignores collection scoping.
- The prefix-dimension "ANN": methodologically unsound.
- The graph schema: untyped string relations with no time, weight or provenance, and manual-only edges. rewire's planned graph should carry `created_at`, a source event id, and validity or supersession at minimum.
- Capacity eviction by age: rewire keeps history in git; forgetting should be a ranking effect, not deletion.
- The weighted-hybrid formula as implemented: it only fires on an unusual path, and the importance input is always 0.

**Combining:** there is no good integration point. CortexaDB could stand in for rewire's vector table, since its Python and Rust APIs exist and the MIT/Apache license is compatible. But it brings no keyword search and no memory semantics, adds a second persistence layer to keep consistent with the markdown/JSONL source, and would need upstream fixes for the issues above. cortex-db has nothing to integrate.

### Gaps
- I did not evaluate how CortexaDB's retrieval quality compares with rewire's on LoCoMo, LongMemEval or similar; no such numbers exist for CortexaDB. Any benefit of ideas 1 and 5 for rewire is untested.
