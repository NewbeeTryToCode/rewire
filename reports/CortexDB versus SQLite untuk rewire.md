# Keep the git brain, upgrade retrieval instead

A CortexDB-style backend is **not** better for rewire than its current storage, and neither is any other database on the list. CortexDB is a third-party, pre-1.0 memory *server*. It runs an LLM extraction pipeline (events → episodes → facts → beliefs) on every write and does ranking on the server. Adopting it would replace rewire's core contract, "files are the source of truth, the index is derived", with a remote store that needs the network, that its operator can read, and that has no documented bulk export. In return rewire would gain features the open evidence does not show to be valuable. In the only reproducible public evaluation, CortexDB flagged **0% of planted conflicts**, belief building added **+0 pp**, LLM fact extraction was **67% of its model cost**, and pre-turn recall took **466 ms to 1.1 s p50**. rewire's local recall takes roughly **4 to 165 ms p50**, and its own diagnoses no longer blame storage for wrong answers. The broader literature points the same way: graph and belief layers rarely beat flat facts plus good retrieval, and published scores track the answer model and pipeline rather than the database. The local alternatives (sqlite-vec, LanceDB, DuckDB, Qdrant Edge, Chroma, pgvector) return the same exact top-k at rewire's scale. They would cost Python/Rust parity and add dependencies, and they gain nothing in quality. rewire should keep markdown + JSONL in git with a derived SQLite FTS5 index. It should spend its effort on a stronger local embedding, an optional local cross-encoder reranker, cheap scan optimisations, and file-derived profile and belief summaries. Separately, rewire's own notes contain three factual errors about CortexDB that need correcting (see the first section).

## Three claims in rewire's notes about CortexDB need correcting

Two documents in the repository describe CortexDB inaccurately: `docs/research/openhuman-hermes.md` (written 2026-10-13) and `docs/evaluation.md`. They should be fixed before anyone uses them as a comparison baseline.

## CortexDB is an LLM pipeline served over HTTP, not a storage engine

CortexDB stores an append-only event log and derives four layers from it with LLMs. Episodes are bounded spans of events. Facts are supersedable triples. Beliefs are confidence-scored claims that get revised. Understanding is a versioned conceptual model. Each layer cites the one below it ([CortexDB layers](https://cortexdb.ai/docs/concepts/layers)). Records are bi-temporal: reads accept `as_of`, `valid_during` and `recorded_during` ([bi-temporal docs](https://www.cortexdb.ai/docs/concepts/bi-temporal)). Retrieval is a hybrid of vector, HNSW and full-text search, with an optional entity graph, HyDE, a multi-hop query planner, salience routing, an optional Cohere rerank and an LLM "verifier" lane ([cortex-flags.md](https://github.com/tinyhumansai/tinymemory/blob/main/docs/evals/cortex-flags.md)). Storage is RocksDB with Raft replication. Every model is an external OpenAI-compatible endpoint, with `gpt-4o-mini` and `text-embedding-3-small` as image defaults. The open client (TinyMemory, GPL-3.0) is a thin layer for orchestration and budgeting. Its `CortexEngine` "exposes no tuning: nearly every knob CortexDB has is a server environment variable" ([cortex-flags.md](https://github.com/tinyhumansai/tinymemory/blob/main/docs/evals/cortex-flags.md)). The product is also young: tags v0.9.13 to v0.11.0 shipped within three weeks, and a label hints at one-way data migrations ([Docker Hub API](https://hub.docker.com/v2/repositories/cortexdb/cortexdb/)).

The evidence for the pipeline's value is thin. The vendor's headline numbers (LongMemEval-S 93.8%, LoCoMo 76.4% to 86.9%) come without visible judge or answer models, and no independent paper or leaderboard evaluates CortexDB ([Mem0 on reading benchmarks](https://mem0.ai/library/agent-memory/how-to-read-memory-benchmarks)). The only open, reproducible numbers come from TinyMemory's small evaluation: 38 to 52 probes, one run, CortexDB v0.10.4. The pack held the answer **95–96%** of the time and the model answered **87–92%** correctly. But **0 conflicts were raised anywhere** under the default `shadow` bi-temporal mode, the synthesis/belief gain was **+0 pp**, and retrieval put the superseded value first in 4 of 5 contradiction probes. The contradictions were only fixed client-side, by prefixing dates so that the reading LLM could choose ([agent-memory.md](https://github.com/tinyhumansai/tinymemory/blob/main/docs/evals/agent-memory.md); [cortex-flags.md](https://github.com/tinyhumansai/tinymemory/blob/main/docs/evals/cortex-flags.md)). Cost is dominated by the write path: of $0.43 per run, **enrichment (fact extraction) was $0.29 (67%)** and belief building $0.07. The authors caution that graph, multi-hop and HyDE are "tuned for … thousands of events", while each scenario held a few dozen. The test therefore did not exercise CortexDB's advanced lanes, so it neither confirms nor refutes them.

## Moving to CortexDB trades rewire's contract for unproven features

rewire's design separates a frozen file contract from a disposable index. Nodes, JSONL events, session summaries and skills live in git. `.index/brain.db` is "derived (not synced)" and "not part of the contract" ([format.md](../docs/design/format.md)). Principle P4 says "the database is only an index that can be rebuilt at any time" ([synaptic-memory.md](../docs/design/synaptic-memory.md)). A CortexDB backend would put the source of truth inside a server. Doing so breaks this principle and also loses Obsidian readability, `rewire undo` through `git revert`, and conflict-free git sync of events (`merge=union`) ([README.md](../README.md)). It would also put server-side automatic extraction in place of rewire's write gate. That gate auto-applies a claim only when it is explicit and user-provided, and sends supersedes and constraints to a human-review inbox ([consolidate.py](../src/rewire/consolidate.py)).

| Dimension | rewire today | With a CortexDB-style backend |
|---|---|---|
| Source of truth | Plain files in a private git repo, human-readable | RocksDB data directory behind an HTTP API; no documented bulk export; OpenHuman removed engine migration and caps scope listing at 1,000 paths ([OpenHuman memory docs](https://github.com/tinyhumansai/openhuman/blob/main/docs/gitbooks/en/features/memory.md)) |
| Offline / privacy | No server, no API, no network at run time ([semantic.py](../src/rewire/semantic.py)) | Network needed unless self-hosted, and even self-hosted it needs embedding and LLM endpoints. Hosted memory "can be read" by the operator; TLS in transit only ([privacy-and-security.md](https://github.com/tinyhumansai/openhuman/blob/main/docs/gitbooks/en/features/privacy-and-security.md)) |
| Recall latency | Rust p50 7–165 ms; LoCoMo p50 4 ms ([Rust A/B](../experiments/eval/results/2026-10-17-ab-rust-gated-expansion.md); [evaluation.md](../docs/evaluation.md)) | pre_turn p50 466 ms–1.1 s, p95 up to 2.1 s, with a 10 s deadline before the pack is dropped ([agent-memory.md](https://github.com/tinyhumansai/tinymemory/blob/main/docs/evals/agent-memory.md)) |
| Write cost | 0 LLM calls for recall and indexing; about 2 LLM calls per session for consolidation ([architecture.md](../docs/design/architecture.md)) | LLM extraction on every write, 67% of model spend; a `learn` acknowledgement means "queued; not yet saved" |
| Conflicts | NEW/SAME/UPDATE/SUPERSEDE/CONTRADICT judge plus human review | Machinery exists, but 0% of planted conflicts were flagged in default mode |
| Determinism | Python and Rust recall identical on 304/304 LoCoMo questions ([iterations.md](../docs/iterations.md)) | Server-side ranking and remote embeddings; not reproducible across versions |
| Cost model | Local | Managed: free tier of 10K memories, Starter $348/yr, Pro $1,788/yr (pricing seen only in search snippets) ([cortexdb pricing](https://www.cortexdb.ai/pricing)) |

The expected improvements are real but small. rewire would get bi-temporal `as_of` queries as a service, an entity graph, automatic belief rollups, HyDE and multi-hop planning, and a vendor that operates the infrastructure. rewire already models most of the first item in files: its L2 claims are "bitemporal, superseded instead of overwritten" ([architecture.md](../docs/design/architecture.md)). The remaining items are retrieval techniques that need no particular storage engine. rewire's own bottleneck analysis also argues against a storage change. LongMemEval_S rose from **78.4% to 85.6%** through recall-pipeline changes alone, on unchanged SQLite, and **all-evidence recall reached 98.3%**. The report concludes that "retrieval is no longer the bottleneck … a stronger answerer, or a judge with the official GPT-4o, is the next lever" ([LongMemEval improvements](../experiments/eval/results/2026-10-16-longmemeval-improvements.md)). No diagnosis in the repo attributes errors to database scale, to database limits, or to a missing server-side graph. One caveat: the benchmarks ran in `episodes` mode, which bypasses rewire's own L2 graph ([evaluation.md](../docs/evaluation.md)). So the value of structured facts is unmeasured on both sides.

## Graph databases and belief layers do not move the scores either

The Zep/Graphiti case shows that a graph store is not the source of benchmark gains. An independent rerun scored Zep Cloud at **74.6%** on LoCoMo. Graphiti, the same temporal-graph data model on Neo4j/FalkorDB/Kuzu but as open source, scored **53.4%** in the same harness, a "21-point gap [that] is real and reproducible" whose cause lies in undisclosed pipeline choices ([a40-labs](https://github.com/agent-memory-atlas-archive/a40-labs--memory)). Controlled ablations agree. "Does Memory Need Graphs?" (ACL 2026) finds that differences are "driven by foundational system settings rather than specific architectural innovations", and that poor graph construction can hurt ([arXiv 2601.01280](https://arxiv.org/abs/2601.01280)). Mem0's graph variant gained about 2.6 points on temporal questions, lost **4.0 on multi-hop**, and roughly doubled p95 latency ([Mem0 paper](https://arxiv.org/pdf/2504.19413)). In the a40-labs rerun, swapping the reader and judge moved scores by 6.9 points, more than the 0.3 to 3.6-point spread between memory stores ([a40-labs](https://github.com/agent-memory-atlas-archive/a40-labs--memory)). Mem0's largest jump, **+20 to +26 points** in 2026, came from *removing* reconciliation, from retrieving the top 200 memories, and from switching to GPT-5 ([Mem0 migration guide](https://docs.mem0.ai/migration/platform-v2-to-v3)). rewire's own entity-based second hop on LoCoMo made results worse (71.3/80.4 against 77.5/82.9) ([LoCoMo analysis](../experiments/eval/results/2026-10-14-locomo-nemotron-s20-analysis.md)).

Write-side extraction is also where errors come from. On HaluMem, Mem0 omits **74%** of updates and Zep 52%, and the graph variant does not fix this ([HaluMem](https://github.com/MemTensor/HaluMem)). Graphiti makes about 6–10 LLM calls per episode. Ingesting LongMemEval-M cost about $7,000 hosted ([a40-labs](https://github.com/agent-memory-atlas-archive/a40-labs--memory)). A 2026 cost study found that "most memory systems have not yet paid back their ingest cost" against full history ([arXiv 2608.11879](https://arxiv.org/abs/2608.11879v1)). Keeping raw user content beat compressed memory on LongMemEval, with substring exact match of 26.0 against 10.7 ([agent-native memory study](https://arxiv.org/html/2606.24775v1)). This supports rewire's choice to keep redacted transcripts next to extracted claims. Bi-temporal invalidation is a pipeline feature that fits in two columns of a relational table. rewire's design notes already reached the conclusion that a personal graph is "far below the point where a dedicated graph DB is needed", with Kuzu at most as an optional index backend ([synaptic-memory.md](../docs/design/synaptic-memory.md)).

## Local vector databases add dependencies, not accuracy, at rewire's scale

Exact brute-force search returns the same top-k vectors in every engine. Swapping the database therefore cannot improve quality; only the embedding, fusion, reranking and chunking can. The question becomes whether any engine is faster or simpler. Measurements made for this research on a 4-vCPU Xeon say none is. Numpy's float32 matvec, the method rewire already uses, scans **100k×256-d in 4.1 ms** and **1M×256-d in 45.7 ms**. sqlite-vec 0.1.9 (brute force only, no ANN index found) took **52.5 ms and 526 ms** on the same data, about 10× slower. Its binary quantization reached 16 ms at 100k but is approximate (measurements by the research team; sqlite-vec's brute-force-only design is also noted by [vectorlite](https://github.com/1yefuwang1/vectorlite)). At rewire's realistic per-user scale of roughly 10³ to 10⁵ items, the scan costs under 4 ms. ANN only becomes relevant near 10⁶ vectors at 256-d, or 10⁵ at 3072-d. At 3072-d, 1M vectors also need about 12 GB of RAM per user.

| Option | What it would add | What it would cost rewire |
|---|---|---|
| sqlite-vec | One C kernel shared by Python and Rust; SQL-side scope filtering | ~10× slower than numpy here; still brute force; pre-1.0 |
| LanceDB | Embedded hybrid BM25 + vector; Rust and Python SDKs ([LanceDB FTS](https://docs.lancedb.com/core/full-text-search)) | New on-disk format and a different BM25, so the tuned weights and parity break |
| Qdrant Edge | In-process hybrid search in Rust with Python bindings ([Qdrant Edge](https://qdrant.tech/edge/)) | Private beta, no GA found; vendor-specific sync |
| DuckDB VSS | HNSW in an analytics engine | HNSW persistence "experimental", no WAL recovery, "do not use … in production" ([DuckDB VSS](https://duckdb.org/docs/current/core_extensions/vss)) |
| Chroma | BM25/SPLADE + vectors ([Chroma sparse](https://www.trychroma.com/project/sparse-vector-search)) | Rust crate is an HTTP client; local use is Python-centred |
| Postgres + pgvector/pgvectorscale | DiskANN at the 50M-vector scale ([pgvectorscale](https://github.com/timescale/pgvectorscale)) | A server process, which conflicts with "does not require a server" |
| Neo4j / FalkorDB (server) | Native graph traversal | Rejected in rewire's design: requires a server and locks the brain into a database ([synaptic-memory.md](../docs/design/synaptic-memory.md)) |

Every engine with its own BM25 implementation would change rankings. Tokenizers and IDF formulas differ, and FTS5 here uses column weights 3/1/2 and `unicode61 remove_diacritics 2`. That would invalidate `SEM_WEIGHT = 0.15` and `EP_SEM_WEIGHT = 0.25` and break the Python/Rust parity rewire currently verifies on every A/B ([index.py](../src/rewire/index.py)). ANN graphs and API embeddings add non-determinism on top of that. The index is derived and swappable by contract, so none of these options is forbidden. Each would simply be a cost with no measured benefit.

### What rewire should do instead or in addition

The levers that matter sit above the storage layer. First, replace or augment WordLlama 256-d with a stronger local model. The static vectors reach R@5 **57% against 90%** for BM25 + keywords ([index.py](../src/rewire/index.py)). The best static retrieval model scores about 82% of all-MiniLM-L6-v2 on MTEB retrieval ([potion-retrieval-32M](https://huggingface.co/minishlab/potion-retrieval-32M)). rewire's own analysis already names "a small contextual encoder (bge-small / e5-small, ONNX)" as the next multi-hop lever, after showing that LoCoMo multi-hop evidence exists but ranks deep: 32.3% all-evidence at 10 excerpts, **79.8% at 100** ([LoCoMo analysis](../experiments/eval/results/2026-10-14-locomo-nemotron-s20-analysis.md)). That rewire-internal 79.8% is an evidence-depth figure, not a J score, and the identical number makes it easy to confuse with the unsourced "CortexDB 79.8%"; how the two got linked was not established. Second, add an optional local cross-encoder over the top 20–50 hybrid candidates. On one 2026 benchmark a 0.6B reranker lifted MRR@10 from **64.2 to 86.1** ([arXiv 2607.24663](https://arxiv.org/pdf/2607.24663)). Third, make the cheap scan fixes: `argpartition` instead of a full `argsort`, which costs about 100 ms at 1M; optional float16 or int8 storage; and similarities rounded before ranking, or int8 dot products, so that numpy and Rust stay bit-identical. Fourth, borrow CortexDB's useful *ideas* as derived files rather than as a server. A per-user profile or belief summary regenerated from L2 nodes would address PersonaMem's weak `suggest_new_ideas` (20–26%) and generalisation (30–46%) questions, which "need the user's whole preference profile" ([PersonaMem report](../experiments/eval/results/2026-10-17-personamem-haiku55.md)). Run `full` mode (facts plus supersede) at scale on LongMemEval and BEAM, so the L2 graph's contribution is finally measured. Fifth, if a CortexDB comparison is still wanted, boot the public image locally as an *evaluation arm*, the way TinyMemory's harness does, with pinned models ([TinyMemory integration](https://github.com/tinyhumansai/tinymemory/tree/main/integration/cortexdb)), rather than as a backend. The remaining gaps worth measuring are `.index/brain.db` size, latency beyond 10,000 nodes, and BEAM 500K/1M.

## Conclusion

The question "CortexDB or SQLite" compares two different layers. CortexDB is an opinionated, LLM-heavy memory *service*. SQLite is an *index* under rewire's own pipeline, which already does extraction, supersession, review and hybrid recall. Every serious comparison in the evidence finds that scores follow the pipeline, the retrieval budget and the answer model, not the database. rewire's data shows its retrieval is saturating (98% all-evidence on LongMemEval), so the next points come from better encoders, reranking and answering. Moving storage would not bring them. A move to CortexDB would therefore pay a large, certain cost in locality, privacy, auditability, determinism and latency for gains that its own integrator could not demonstrate.

The more useful takeaway is that rewire's design already isolates this decision. Because the index is derived, any future engine (sqlite-vec with ANN, Qdrant Edge, Kuzu) can be tried behind the same file contract when a user actually approaches 10⁶ vectors, and rolled back by deleting `.index/`. Meanwhile, the corrected record matters. rewire's evaluation should not chase an unsourced "79.8%" target, or describe a self-hostable Apache-2.0-labelled image as a closed in-house server. Credible comparisons need pinned, locally reproducible runs, which is the same discipline rewire already applies to Mem0 and Graphiti.
